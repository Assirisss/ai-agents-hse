# Финансы и инвестиции

Реализованный локальный MVP: доходы, расходы и переводы в RUB, сайт и Telegram с общими данными Postgres, распознавание чеков в проверяемые черновики, детерминированная статистика, наблюдение за акциями MOEX TQBR и ежедневная фактическая сводка. Инвестиционных советов, торговых действий и прогнозов нет.

## Запуск

Node.js 24, npm; для базы нужен Docker Compose либо установленный Postgres. Из корня:

```sh
docker compose up -d postgres
cd backend
npm ci
cp .env.example .env
npm run finance:migrate
npm run dev
```

Если `.env` уже есть, дополните его переменными из примера вместо перезаписи. `DATABASE_URL` в примере соответствует локальному Compose. Сервер применяет версионируемые миграции и при старте. Postgres слушает только `127.0.0.1`. `npm start` запускает собранный backend после `npm run build`.

В другом терминале:

```sh
cd frontend
npm ci
npm run dev
```

Откройте «Финансы». По умолчанию есть счёт «Наличные» с нулевым начальным остатком и базовые категории. Добавьте свои счета и начальные остатки в настройках. Без `DATABASE_URL` исследователь трендов продолжает работать, а финансовые запросы возвращают явную ошибку настройки.

## Модель и Telegram

Ручной учёт, простые текстовые команды, уточнения диалога и котировки работают без LLM. Для сложных текстовых запросов задайте `FINANCE_TEXT_URL`, `FINANCE_TEXT_MODEL`, при необходимости `FINANCE_TEXT_API_KEY`. Для чеков — отдельные `FINANCE_VISION_URL`, `FINANCE_VISION_MODEL`, `FINANCE_VISION_API_KEY`. URL — адрес OpenAI-совместимого API: например, `https://openrouter.ai/api/v1` или `http://127.0.0.1:8000/v1` для будущего vLLM. Конкретный идентификатор модели выбирается явно, скрытой подмены модели нет. Текстовая модель должна поддерживать tools, визуальная — изображения и JSON. Совместимость выбранного провайдера нужно проверить на демонстрационных данных.

Профильные финансовые записи, выбранные инструментом, передаются текстовой модели; изображение чека — визуальной модели. При API-провайдере данные покидают устройство. Самостоятельное размещение подключается заменой URL/модели, но GPU, модели и RunPod этим репозиторием не разворачиваются.

Для Telegram:

1. В локальном backend `.env` задайте `TELEGRAM_BOT_TOKEN` и необязательный `TELEGRAM_BOT_USERNAME` без `@`.
2. Перезапустите API и в отдельном терминале backend запустите `npm run finance:worker`.
3. На сайте, в настройках финансов, получите одноразовый код; отправьте боту `/start КОД`. Код действует 10 минут и хранится в базе как SHA-256. Пока код показан и действует, сайт автоматически проверяет статус привязки. Повторный `/start` в уже привязанном финансовом чате подтверждает действующее подключение; использованный код повторно не применяется.
4. Отправьте сообщение или фото чека. Заполните отсутствующие поля и нажмите «Подтвердить».

После объединения с делами и календарём входящие сообщения получает один общий бот в процессе API. Финансовый worker занимается только ежедневной доставкой и не вызывает getUpdates. Другой backend/webhook с тем же токеном не должен забирать обновления. Поддержаны только личные чаты. Привязка проверяется одновременно по пользователю и чату; повторно полученные update ID не выполняются ещё раз. При сбое процесса между сохранением update ID и окончанием обработки действие может остаться незавершённым: проверьте черновики на сайте и повторите ввод. Гарантия exactly-once для внешних сообщений не заявляется.

Финансовые команды: `/finance текст` (либо `/finance` для помощи), `/income`, `/expense`, `/transfer`, `/accounts`, `/categories`, `/drafts`, `/balance`, `/expenses`, `/period`, `/operations`, `/summary`. `/cancel` отменяет текущий финансовый черновик. `/help` показывает общую помощь бота. Если чат привязан также к планированию, свободный текст по умолчанию идёт туда; расходы лучше задавать через `/finance`. Фото чеков и исправления текущего финансового черновика направляются в финансы. Поля черновика можно менять сообщениями: `сумма 350,50`, `дата 2026-10-18`, `счёт Наличные`, `категория Продукты`, `тип расход`, `описание Продукты`. Новый ввод при наличии текущего черновика начинается после его подтверждения либо `/cancel`.

Для постоянной работы держите API, Postgres и worker запущенными. Worker публикует сводку после 21:00 Europe/Moscow; после перезапуска догоняет только сегодняшний пропуск. Без привязанного чата или бумаг рассылки нет. `npm run finance:worker:start` — запуск собранного worker.

## Проверяемый учёт

- Суммы — целые копейки; остатки и статистику считает сервер. Доходы/расходы исключают переводы; перевод атомарно меняет два счёта. Категория должна соответствовать типу операции.
- Текст и чек создают черновик. Неизвестные сумма и счёт не подставляются автоматически. Для свободного текста и чека неизвестная дата остаётся пустой; явные команды `/income`, `/expense`, `/transfer` без даты используют сегодня и показывают это допущение. Без обязательных полей подтверждение отклоняется. Модель не имеет инструмента подтверждения.
- Проверяется схема ответа модели и соответствие суммы исходному тексту. Это не доказывает правильность распознавания: итог нужно сверить с чеком перед подтверждением.
- Фото: JPEG/PNG/WebP до 10 МБ; метаданные в Postgres, изображения в закрытом каталоге `FINANCE_RECEIPT_DIR` (по умолчанию `backend/data/finance-receipts` при запуске из backend). Путь не принимается от клиента, выдача проверяет профиль. Хеш отмечает повторную загрузку, совпадение суммы/даты/счёта — вероятный дубликат операции.
- Один чек создаёт одну расходную операцию, позиции — расшифровка. Расхождение итога и суммы строк видно как предупреждение: скидки и неполное распознавание требуют проверки.
- Редактирование и отмена записей сохраняют историю; повторное подтверждение одного черновика возвращает прежнюю операцию. Отмена не удаляет аудит.
- У черновика есть `revision` (для старых записей без этого поля — `0`). HTTP-сохранение и подтверждение требуют `expectedRevision`; проверка выполняется внутри транзакции, устаревший запрос получает `409` без изменения данных. После сохранения версия увеличивается. Сайт подтверждает показанную версию отдельным запросом без повторного сохранения полей. Старая кнопка Telegram показывает новый черновик для повторной проверки и подтверждения.
- Записанная операция также имеет `revision`, начиная с `0` (старые записи без поля считаются версией `0`). Для `PATCH /operations/:id` обязателен `expectedRevision`. Проверка и увеличение версии выполняются под финансовой блокировкой в одной транзакции. Сохранение из старого окна получает `409` и не меняет операцию, баланс или аудит; обновите данные, проверьте поля и повторите правку.
- При обновлении сайта нетронутые поля формы получают актуальные значения. Если есть несохранённые правки и серверный черновик изменился, форма сохраняет введённый текст и блокирует запись до загрузки актуальных полей явной кнопкой.
- Сравниваются два соседних периода одинаковой длины. Сводка контекста трендов передаёт только доходы и расходы с начала месяца; чеки не передаются.

## Команды, диалоги и проверяемые ответы

Примеры для сайта и Telegram без модели:

```text
/expense 850 продукты; счёт Наличные; дата сегодня
/income 10000 зарплата; счёт Карта
/transfer 500; со счёта Карта; на счёт Наличные
/accounts
/categories
/drafts
/balance
/expenses
/period прошлый месяц
/operations 2026-10-01 2026-10-18
```

Счета и категории должны существовать в вашем профиле. Несколько сумм, несколько подходящих счетов, несуществующая дата или отрицательная сумма приводят к уточнению, а не угадыванию. Для свободного текста «Потратил 850 рублей на продукты» можно следующим сообщением уточнить «Сегодня, со счёта Наличные». Дата расхода не сдвигается в будущее по правилам календарного планирования.

Команды добавления используют сегодняшнюю дату только как явное правило команды; на черновике это видно. Во всех режимах сумма хранится в копейках, подтверждение финансовой операции остаётся отдельным действием пользователя. Команды не вызывают модель. Сложный запрос при настроенной модели проходит ограниченный агентный цикл; произвольные финансовые утверждения модели не подменяют результаты серверных расчётов.

История финансового чата, текущий черновик и выбранные фильтры хранятся в Postgres. В браузере остаётся только ID выбранного диалога. «Расходы за этот месяц» → «А за прошлый месяц?» → «Только по карте» сохраняют контекст фильтра. В ответе есть переход к подтверждённым операциям, из которых он сформирован. Ответ содержит снимок IDs и числа операций; при последующем изменении учёта текущая выборка может отличаться, что пояснено в интерфейсе.

Каждое сообщение имеет `turnId`, отпечаток тела запроса и `expectedRevision`. Повтор того же запроса возвращает уже сохранённый ответ; повтор идентификатора с другим телом и устаревшая версия отклоняются. Версия проверяется внутри транзакции Postgres, поэтому защита работает между процессами и после перезапуска. В одном диалоге до 100 обменов, список показывает последние 40 диалогов. Автоматической очистки пока нет.

Агент работает на частной копии состояния. История сообщения, создание/изменение черновика и аудит переносятся в основную базу короткой транзакцией после завершения; во время обращения к модели финансовая блокировка не удерживается. Отмена до коммита не сохраняет незавершённые изменения. Если соединение оборвалось после коммита, обновите диалог или повторите тот же `turnId`: сохранённый результат будет возвращён. Параллельная правка черновика на сайте не перезаписывается ответом модели. Telegram использует стабильный ID обновления для своего обмена.

Для каждого заполненного поля черновика показаны метод (`manual`, `rule`, `model`, `receipt`), исходный фрагмент при наличии и пояснение допущения. При ручном изменении метка обновляется. Эти сведения помогают проверить результат, но не доказывают правильность распознавания.

## Анализ финансов и роль агента

В помощнике доступны пять сценариев:

| Запрос | Что рассчитывается |
| --- | --- |
| «Почему в этом месяце потратил больше?» | Расходы за равные периоды, положительный и отрицательный вклад категорий; возможная разовая покупка требует проверки. |
| «Есть ли необычные расходы?» | Необычные суммы относительно предшествующей истории категории и возможные дубликаты. Это кандидаты для проверки, не вывод о мошенничестве. |
| «Найди мои регулярные платежи» | Кандидаты в еженедельные/ежемесячные платежи по истории за 180 дней; подписка не подтверждается и напоминание не создаётся автоматически. |
| «Что будет, если сократить продукты на 20%?» | Сокращение выбранных прошлых расходов на явно указанный процент, с округлением до копейки. Это сценарий, а не прогноз. Если параметров не хватает, помощник уточняет их. |
| «Как прошла моя финансовая неделя?» | Доходы, расходы, разница, изменения категорий за последние 7 дней и ближайшие сохранённые напоминания. Плановые платежи не прибавляются к расходам. |

По умолчанию сравнение расходов использует одинаковое количество прошедших дней соседних месяцев. Если предыдущий месяц короче, обе выборки ограничиваются одинаковым количеством дней; исключённые даты показаны в ограничениях. Можно задать свой период (`YYYY-MM-DD YYYY-MM-DD`) либо два равных непересекающихся периода четырьмя датами. Изменение категорий объясняет арифметический вклад в итог, но не устанавливает причину поведения человека. Отсутствие записей не доказывает нулевые реальные расходы.

Для необычных сумм берутся 90 дней до выбранного периода и минимум 5 записей категории на 3 разных датах. Порог — максимум из удвоенной медианы и медианы плюс три медианных абсолютных отклонения. Повторения требуют минимум 3 разных дат, одинаковых счёта/категории/нормализованного описания, интервалов 6–8 либо 26–33 дня и сумм в пределах 10% от медианы. Эти эвристики консервативны и могут пропускать реальные повторения и ошибки.

Запросы анализа проходят отдельным маршрутом, поэтому общие слова «расходы» и «сколько» больше не перехватывают их обычной статистикой. Сначала рассчитывается базовый отчёт. При настроенной модели агент читает его, сам выбирает дополнительную детализацию категорий и собирает объяснение через `finance_explain_analysis`. Инструмент принимает только ID уже рассчитанных фактов и предположений; неизвестные ID и попытка выдать предположение за факт отклоняются. Общий итог, ключевые показатели и ограничения сохраняются в ответе. Произвольные финансовые утверждения из текста модели не показываются.

Расчёты доступны без LLM; при сбое модели показывается полный базовый отчёт с явным пояснением. Аналитический агент получает только инструменты чтения, не создаёт черновиков и не меняет операции. Диалог сохраняет отчёт и источники; повтор одного `turnId` возвращает сохранённый результат.

На сайте отдельно показаны факты, предположения и ограничения данных. Источники ссылаются на конкретные ID операций, включая предыдущий период. В журнале отображается текущее состояние этих записей; отменённые операции могут исчезнуть из выборки. Ручное изменение фильтров снимает ограничение по ID снимка. В Telegram отправляется тот же текстовый отчёт с разделами и примерами операций.

Инструменты: `finance_compare_expenses`, `finance_expense_breakdown`, `finance_unusual_expenses`, `finance_recurring_expenses`, `finance_spending_scenario`, `finance_weekly_summary`. Они экспортируются вместе с остальными финансовыми инструментами; профиль закрепляется сервером. Отдельный `POST /api/finance/analysis` с `{kind, from?, to?, previousFrom?, previousTo?, accountId?, categoryId?, query?, reductionPercent?}` позволяет проверить расчёт без агента. Виды: `changes`, `breakdown`, `unusual`, `recurring`, `scenario`, `weekly`; период ограничен 366 днями, будущие даты не принимаются.

## Напоминания о платежах

На вкладке «Платежи» укажите название, первый срок, время (по умолчанию 09:00 Europe/Moscow), необязательные сумму/счёт/категорию и однократное, еженедельное либо ежемесячное повторение. Создаётся связанная задача в общем разделе «Дела и календарь». Задачи не синхронизируются с внешними календарями Google/Яндекса; это существующее ограничение планирования.

Финансовое обязательство сначала сохраняется в Postgres, затем синхронизируется с календарём по стабильному ID. Сбой между этими шагами виден как `pending/error`; повторное обновление восстанавливает связь без второй задачи. Отмена затрагивает только задачи с проверенным маркером этого платежа и профиля.

Для финансовых задач используется отдельный журнал доставки, чтобы общий календарный планировщик не присылал второе уведомление. Напоминание просроченной открытой задачи догоняется после простоя и отправляется один раз на её фактический срок; определённые ошибки повторяются до трёх раз, неоднозначный ответ Telegram остаётся `uncertain` без автоматического повтора. Требуются запущенный API и финансовая привязка Telegram. Отдельный worker котировок для этих напоминаний не нужен.

Выполнение задачи не создаёт расход. Кнопка «Записать фактическую оплату» только готовит черновик, где нужно проверить дату, сумму и остальные поля. Учёт факта оплаты и выполнение задачи — отдельные действия. Для повторяющейся задачи следующий срок появляется после выполнения предыдущей. Правило на 29–31-е число пропускает месяцы, в которых такого дня нет; это показано в форме.

## Котировки и доставка

Источник — официальный [MOEX ISS](https://www.moex.com/a2193). Список ограничен акциями TQBR в рублях, до 10 бумаг, начальный список пустой. Публичные котировки могут предоставляться с задержкой. В отчёте есть источник, дата сделки и время получения; технический timestamp обновления не считается датой сделки.

Изменение рассчитывается относительно предыдущего торгового закрытия. При отсутствии текущей сделки используется датированная торговая история, при ошибке — явно устаревший сохранённый результат либо «данные недоступны». Выходные не подменяются сегодняшней датой. Сообщение формируется обычным шаблоном, без LLM. Доступность источника проверяется реальным запросом отдельно от тестов.

Задания и статусы доставок хранятся в Postgres. Однозначные ошибки повторяются с интервалом не меньше минуты, максимум три попытки за дату; неоднозначная отправка или оборванный статус `sending` становятся `uncertain`, без автоматического повтора. Это снижает риск дублей, но не гарантирует однократную доставку Telegram. Журнал виден в настройках сайта.

## Контракты и интеграция

Типы — `shared/finance.ts`. HTTP-методы работают под `/api/finance`, `profileId` задаётся query-параметром (по умолчанию `default`). В текущем UI используется `default`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /state`, `GET /stats?from=YYYY-MM-DD&to=YYYY-MM-DD` | Состояние и статистика |
| `POST /accounts`, `PATCH /accounts/:id`, `POST /categories` | Счета и категории |
| `POST /drafts`, `PATCH /drafts/:id` | Создать / исправить черновик; PATCH: поля и обязательный `expectedRevision` |
| `POST /drafts/:id/confirm`, `POST /drafts/:id/cancel` | Подтверждение с `{expectedRevision}` / отмена |
| `PATCH /operations/:id`, `POST /operations/:id/cancel`, `GET /operations/:id/audit` | Исправления и аудит; PATCH: поля и обязательный `expectedRevision` |
| `POST /analysis` | Расчёт аналитического отчёта без модели |
| `POST /agent` с `{text}` | Совместимый вход: команды, диалог, модель только для сложного запроса |
| `GET /chat/conversations`, `POST /chat/conversations` | Список / создать диалог |
| `GET /chat/conversations/:id` | История и состояние диалога |
| `POST /chat/conversations/:id/messages/stream` | `{turnId, expectedRevision, text}`, NDJSON progress/result/error; отмена потоком |
| `GET /payments`, `POST /payments` | Список / создать напоминание |
| `POST /payments/:id/cancel`, `POST /payments/:id/draft` | Отменить напоминание / подготовить факт оплаты для подтверждения |
| `POST /receipts` | Изображение в raw body, Content-Type `image/*`, `X-Filename` в URL-кодировке |
| `POST /receipts/:id/recognize`, `GET /receipts/:id/image` | Распознать / посмотреть чек |
| `GET /instruments?query=`, `POST /watchlist` с `{ticker}`, `DELETE /watchlist/:ticker` | Отслеживаемые бумаги |
| `POST /summary` | Получить и сохранить фактическую сводку |
| `POST /telegram/link`, `DELETE /telegram/link` | Код привязки / отключение |
| `GET /context` | Агрегаты для общего контекста разделов |

`createFinanceTools(financePort(service, profileId))` экспортирует описания, JSON Schema и исполнение инструментов для будущего общего агента. Профиль задаёт вызывающий сервер, аргументы модели не позволяют выбрать чужой профиль. Общий оркестратор ещё не реализован. Whisper, графовый RAG и банковские интеграции не требуются для этого MVP.

## Проверки и демонстрация

```sh
cd backend
npm test
npm run eval:finance
npm run build
npm run finance:seed-demo
```

`finance:seed-demo` сбрасывает **только** профиль `demo` и записывает искусственные операции; `default` не меняется. Демоданные доступны API с `?profileId=demo`. Для повторяемых агентных проверок используются отдельные фиксированные тестовые сценарии.

Чтобы выполнить проверку настоящей Postgres, задайте `FINANCE_TEST_DATABASE_URL` адресом отдельной тестовой базы и запустите `npm test`. Этот тест применяет миграции и создаёт профили с префиксом `test_`; без переменной он явно пропускается. Остальные тесты используют память, подставные модели и HTTP-ответы, без внешних вызовов и реальных сообщений.

```sh
cd frontend
npm run lint
npm run build
```

Демонстрация: добавить счёт → сообщение/фото → исправить сумму/дату/категорию → убедиться, что баланс не менялся → подтвердить → проверить операцию, статистику и историю → отменить → выбрать бумаги → посмотреть датированную сводку → привязать Telegram.

## Ограничения эксплуатации

Это локальный прототип: `profileId` разделяет данные, но не является авторизацией сайта. API слушает loopback; до публикации нужны полноценная аутентификация и авторизация, TLS, квоты, резервное копирование базы и каталога чеков. Политика автоматического удаления чеков/аудита не реализована. Для MVP состояние загружается целиком, поэтому большие объёмы операций потребуют пагинации и более узких запросов. Временные тесты не подтверждают доступность выбранных моделей, MOEX или Telegram в среде развёртывания.
