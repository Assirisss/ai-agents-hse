# Runpod для спорта и питания

Дневник работает самостоятельно; четыре AI-операции подключаются только к отдельному Runpod Serverless endpoint. Тренды, гардероб и BiRefNet сохраняют свои подключения. Конфигурация: [services/health/runpod.json](../services/health/runpod.json).

## Что потребуется

1. Аккаунт Runpod с положительным балансом. Согласованный бюджет — **до $20 в месяц**. Пополнение выполняет владелец аккаунта.
2. Отдельный серверный `HEALTH_RUNPOD_API_KEY` в закрытом `backend/.env`: GraphQL **None**, `api.runpod.ai` — **Restricted → health endpoint → Read / Write**. Не отправляйте ключ в чат, не добавляйте его во frontend или Git. Авторизация MCP сама по себе не авторизует приложение. Общий `RUNPOD_API_KEY` сохраняет права для других разделов; ограничение только спортивным endpoint относится к отдельному ключу спорта.
3. Отдельный endpoint с `Qwen/Qwen3-VL-8B-Instruct`. Существующая Qwen3-4B — текстовая, для фото не подходит. В выбранной публичной модели нет требования принимать gated-лицензию Hugging Face.

## Создание endpoint

В Runpod Hub выберите официальный `runpod-workers/worker-vllm`, release `v2.29.0`, и создайте **новый** Serverless endpoint. Не изменяйте существующие endpoint других разделов. [Инструкция Runpod](https://docs.runpod.io/serverless/vllm/get-started).

Начальные параметры:

| Параметр | Значение |
| --- | --- |
| Model | `Qwen/Qwen3-VL-8B-Instruct` |
| GPU | A40 / RTX A6000, **48 ГБ**, один GPU |
| Active/min workers | **0** |
| Max workers | **1** |
| Idle timeout | **1 секунда** |
| FlashBoot | Включён |
| Execution timeout | **90 секунд** |
| Container disk | **40 ГБ** |
| Network volume | Не подключать на первом этапе |

Модель содержит 8 767 123 696 параметров: при двух байтах на параметр веса занимают около 17,53 ГБ (16,33 ГиБ), до дополнительных буферов. При запуске на A40 лог показал 16,77 ГиБ для загрузки модели, 2,26 ГиБ пиковых активаций и 18,52 ГиБ KV-кэша. Поэтому текущая конфигурация рассчитана на 48 ГБ; перенос на 24 ГБ потребует отдельных настроек и проверки. [Метаданные модели](https://huggingface.co/api/models/Qwen/Qwen3-VL-8B-Instruct).

В Advanced/Environment Variables перенесите `env` из JSON. Worker v2.29.0 возвращает исходный ответ vLLM; дополнительный флаг `RAW_OPENAI_OUTPUT` для этой версии не требуется. `MAX_MODEL_LEN=16384`, `MAX_NUM_SEQS=1`, `MAX_CONCURRENCY=1`, `MAX_NUM_BATCHED_TOKENS=8192`, одно изображение и eager mode ограничивают память и компиляцию при запуске. Логирование запросов и ответов vLLM отключено. Образ требует CUDA 13.0: ограничение хоста также указано в JSON. Если Hub поменял форму настройки, сверяйте реальные параметры с JSON перед созданием.

Ревизии модели и токенизатора зафиксированы в JSON. Поле `verifiedImageDigest` содержит digest, прочитанный из лога загрузки контейнера. Проверка 19 октября 2026 года подтвердила совместимость на A40; результаты всех пяти сценариев приведены ниже.

## Подключение приложения

В `backend/.env`:

```dotenv
HEALTH_RUNPOD_API_KEY=your_health_only_private_key
HEALTH_RUNPOD_ENDPOINT_ID=your_new_endpoint_id
HEALTH_RUNPOD_MODEL=Qwen/Qwen3-VL-8B-Instruct
HEALTH_AI_MONTHLY_REQUEST_LIMIT=100
```

Перезапустите backend (`cd backend && npm run dev`), затем запустите frontend в отдельном терминале (`cd frontend && npm run dev`). Во вкладке «Тренер» появится подключение Runpod и счётчик запросов. Наличие конфигурации не гарантирует готовность удалённого GPU: реальные ошибки отображаются после запроса. Пустой `HEALTH_RUNPOD_ENDPOINT_ID` отключает AI, оставляя ручной дневник доступным.

Приоритет ключей: непустой `HEALTH_RUNPOD_API_KEY`, затем общий `RUNPOD_API_KEY` для совместимости. Выбор фиксируется при запуске. Ответ 401/403 не запускает повтор с другим ключом. Существующие ключи, их права и настройки других модулей приложение не изменяет.

Неверный формат endpoint, отсутствие обоих ключей или некорректная квота отключают только спортивный AI. Backend, ручной дневник и остальные разделы продолжают работать. Причина доступна в `GET /api/sport/capabilities` как `aiUnavailable: { code, message }`; `code` — `not-configured` или `invalid-configuration`, при готовой конфигурации поле равно `null`. Ответ `status: unavailable` содержит ту же причину. Сервер выводит одно предупреждение с именами ошибочных настроек, без значений и секретов.

Квота должна быть целым числом от 0 до 10000; пустое значение означает 100. Неверное значение отключает AI с внутренним лимитом 0. Корректный 0 блокирует отправку существующим механизмом квоты. При запуске сетевых проверок и списаний нет; наличие конфигурации не означает, что Runpod проверил ключ или готов обработать запрос.

## Расходы и остановка

Счётчик SQLite общий для профилей, сохраняется после перезапуска и ограничивает **попытки отправки** за календарный месяц UTC. Ошибки и отменённые отправки тоже учитываются. Это ограничение числа запросов, **не жёсткий денежный лимит**.

Runpod тарифицирует время работы worker, включая загрузку модели и ожидание перед выключением; хранение оплачивается отдельно. `delayTime` включает очередь и не равно оплаченной загрузке. Поэтому приложение не выдаёт вычисленную по нему сумму за реальный счёт. [Тарификация](https://docs.runpod.io/serverless/pricing).

При бюджете $20 проверяйте расходы именно health endpoint в Billing после первых запросов. Заложите запас на запуск, хранение и тесты; отключите автоматическое пополнение, если хотите ограничить общие расходы балансом. Баланс общий с другими endpoint и не является отдельной квотой спорта. Стартовый лимит 100 попыток можно уменьшить до получения замеров.

Для остановки: `HEALTH_AI_MONTHLY_REQUEST_LIMIT=0` блокирует новые запросы приложения; очистка ID отключает тренера. В Runpod установите **min=0, max=0** и проверьте, что текущие задачи завершены/отменены и активных worker нет. Хранилище, если создано отдельно, может продолжить оплачиваться.

## Поведение и проверка качества

Текст тренировки превращается в черновик с пропусками неизвестных чисел. Предложение тренировки использует каталог, рабочий вес всегда вводит пользователь. Фото блюда даёт предположения о продуктах и массе; фото этикетки — проверяемые значения на 100 г. КБЖУ считаются кодом только после выбора продукта и подтверждения массы. Для прогресса backend рассчитывает показатели и формирует допустимые выводы. Модель получает только эти выводы, выбирает и упорядочивает от 1 до 12 уникальных ID в `{ "insightIds": [...] }`. Тексты, числа, вопросы и предупреждения формирует backend; личные заметки не передаются.

Живые проверки выявили ошибочные свободные комментарии модели о съедобности и наличии упражнения в справочнике. Поэтому пояснения к фото и тренировкам формирует backend, вопросы строятся по пропущенным полям, а имя, тип и признак собственного веса известных упражнений берутся из каталога. Несопоставленное упражнение можно сопоставить с любым элементом каталога либо исправить его тип и создать новое. Для кардио собственный вес отключён; при смене типа несовместимые измерения очищаются без преобразования повторений в минуты. Эти случаи покрыты отдельными регрессионными тестами. Неизвестные/повторяющиеся ID, свободные комментарии и лишние поля ответа прогресса отклоняются. Пустой период имеет специальный вывод `no-data`; отсутствие записей не трактуется как отсутствие еды или активности. Это проверка соответствия дневнику, а не подтверждение полноты дневника или точности распознавания фото.

Каждый запрос создаёт одну задачу `/run`, затем опрашивает `/status`. Ожидание ограничено пятью минутами. Отмена и тайм-аут вызывают `/cancel` по возможности; при сетевом сбое отмену нельзя гарантировать. Автоматических повторов и перехода к другим провайдерам нет. Фото нормализуется с удалением метаданных. Модель не имеет доступа к сохранению записей, ключам и другим профилям.

Офлайн-проверки:

```sh
cd backend
node --import tsx --test src/tests/health*.test.ts
npm run build
```

Явная **платная** проверка — пять запросов с синтетическими данными в отдельной базе в памяти, без личного дневника: тренировка, изображение без еды, читаемая этикетка, пустой период прогресса и предложение тренировки. Вывод содержит ID задач, статус, время и проверенные результаты, без ключа:

```sh
npm run build
node scripts/check-health-runpod.mjs --live
# Только выбранные проверки, без повторения остальных:
node scripts/check-health-runpod.mjs --live --only=label,progress,suggestion
# Ровно две проверки нового контракта прогресса:
node scripts/check-health-runpod.mjs --live --only=progress,progress-populated
```

Дополнительный `progress-populated` создаёт синтетические записи в отдельном профиле базы в памяти: 1 тренировка, 105 ккал за 1 день, кардио без расстояния и самочувствие 4/5. Скрипт сверяет возвращённые формулировки с серверными заготовками и проверяет отсутствие изменений дневника моделью. Квота скрипта отдельная, число запросов ограничено выбранными сценариями; расходы этих проверок учитывайте отдельно от счётчика рабочего дневника.

Проверка подтверждает транспорт и базовые ответы, но не доказывает точность КБЖУ. До использования оценок порций соберите отдельный набор взвешенных блюд и этикеток: проверяйте распознавание, ошибки массы и КБЖУ, пропуски/выдуманные продукты, время и стоимость. Проверочную часть не используйте для настройки промпта. Сохраняйте версию модели и параметры каждого прогона.
