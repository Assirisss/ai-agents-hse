# Инструменты стилиста: фото и изменения через чат

Пользователь пишет задание и прикрепляет фотографии. Наличие фото само по себе не запускает распознавание или запись. Модель выбирает инструмент, платформа выполняет его и возвращает фактический результат; затем модель решает следующий шаг. Переключатель автодобавления и предварительная обработка до решения модели удалены.

## Инструменты

| Инструмент | Контракт и эффект |
| --- | --- |
| `wardrobe_inspect_image` | `imageId`, необязательный `focus`; распознаёт вещь, тип, название, описание, цвет и сезон. Не изменяет каталог. |
| `wardrobe_remove_background` | `imageId`; вызывает существующий BiRefNet, сохраняет исходник, возвращает новый `imageId` с прозрачным фоном. Показывает результат в чате. |
| `wardrobe_add_from_image` | `imageId`, необязательные уточнение и явно заданные исправления; внутри вызывает распознавание, заполняет поля и сохраняет вещь с фотографией. Возвращает записанную карточку и квитанцию. |
| `wardrobe_update_garment` | Реальные `garmentId`, `expectedUpdatedAt`, только изменяемые поля. Сразу изменяет описание по запросу в чате; остальные поля и фото сохраняются. |
| `wardrobe_replace_photo` | Реальные ID и версия вещи, `imageId`; заменяет фото, сохраняет описание. |
| `wardrobe_search_trends` | Короткая публичная `topic` из запроса и аспект `focus`; делегирует исследование существующему агенту трендов, возвращает источники, даты и ограничения. |

Примеры цепочек:

- «Что на фото?» → inspect → ответ без добавления.
- «Добавь эту вещь» → add (внутри inspect) → подтверждение записи.
- «Убери фон и добавь» → remove → add с новым imageId.
- «Переименуй мою белую футболку» → search → update.
- «Замени фото футболки этим снимком» → search → replace.
- «Убери фон у фотографии моей куртки» → search → remove → replace.
- «Какие сумки сейчас актуальны?» → research → ответ с источниками.

Это варианты поведения, описанные модели, а не маршрутизация по ключевым словам. Неясное намерение или несколько равноправных вещей на фото требуют уточняющего вопроса в чате.

## Исполнение и хранение

Текстовый агент работает на backend и выбирает инструменты стандартными function calls. Его поток NDJSON включает `tool_request` с проверенными аргументами и одноразовым непрогнозируемым токеном. Браузер исполняет разрешённый инструмент над своей IndexedDB и возвращает результат через `POST /api/wardrobe/agent/tool-results/:token`. Сервер проверяет схему, токен и ID ожидаемого вызова; результат возвращается модели в сообщении `tool` с исходной корреляцией. Успешно записанная карточка обновляет снимок и доступна поиску в том же запуске.

Браузерное исполнение необходимо, поскольку личный гардероб хранится в браузере. Backend не получает произвольный доступ к IndexedDB или файлам. Вложения и результаты обработки сохраняются в отдельной базе `${repository.namespace}:stylist-images-v1`; в историю чата и контекст модели попадают только ссылки и характеристики. Это позволяет следующим сообщением сказать «теперь добавь» или «сохрани без фона». Оригинал и отображаемая версия хранятся раздельно. Доступ к вложениям ограничен ссылками текущего диалога; фото вещей доступны по ID реальных записей гардероба.

Добавление одного вложения использует постоянную квитанцию и не создаёт дубль при повторном вызове, в том числе в следующем сообщении. Изменения и квитанции используют существующую атомарную транзакцию `agentActions`. Изменение карточки/фото проверяет `expectedUpdatedAt`; устаревший запрос не перезаписывает более новую запись. Успешные квитанции сразу появляются и сохраняются в чате, даже если последующий ответ модели прервётся. Отмена до записи не создаёт вещь; отмена после завершённой транзакции не отменяет выполненный результат. Закрытие потока отменяет ожидание и удаляет незавершённые токены.

До 8 обращений к модели, 12 инструментов и одного исследования трендов. Чат с браузерными инструментами ограничен 15 минутами, чтобы вместить холодный запуск CV; тайм-аут отдельного распознавания — 90 секунд, удаления фона — 10 минут. Не более двух одновременных запусков. Дополнительных форм и переключателей для выбора инструментов нет. Ранее подготовленные карточки образов/покупок продолжают работать.

## Модели и ограничения

Текст и инструменты используют общий настроенный Runpod / OpenRouter / Ollama. Распознавание изображений отдельно использует `OPENROUTER_API_KEY`, модель по умолчанию `dots-studio/dots-3-note-preview:free`, переопределение `WARDROBE_VISION_MODEL`. Для явно бесплатной основной модели запрос включает запасную `nvidia/nemotron-3.5-super-vl:free` через штатный `models` routing OpenRouter: до двух бесплатных моделей в одном API-запросе, без платного fallback. Для произвольно настроенной платной модели автоматический резерв не добавляется. [Контракт резервирования OpenRouter](https://openrouter.ai/docs/guides/routing/model-fallbacks). BiRefNet использует существующие `RUNPOD_API_KEY` и `RUNPOD_BIREFNET_ENDPOINT_ID`. Новая инфраструктура и автоматический переход на платные модели не создаются.

Браузер принимает до трёх JPG/PNG/WebP за сообщение (15 МиБ, 40 Мп на исходник). Для vision готовится уменьшенная копия; сервер проверяет формат, удаляет EXIF и ограничивает размер до 2 МиБ/1024 px. Только вызов image-инструмента отправляет копию специализированной модели. Цены, бренд, состав и размер не угадываются. Неполный JSON, тайм-аут, неоднозначность и отказ модели не считаются успешной записью.

Контракты и обработчики имеют проверяемые параметры и эффекты. Сам выбор инструментов и распознавание нейросетью не гарантируют одинаковый результат при одинаковом запросе: детерминированными являются проверки, вычисления и операции хранения.

Применены рекомендации [Anthropic о ясных инструментах, результатах и оценке задач](https://www.anthropic.com/engineering/writing-tools-for-agents), [агентном цикле с обратной связью от среды](https://www.anthropic.com/engineering/building-effective-agents) и [протоколе tool calling OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling). Протокол изображения: [Image Understanding](https://openrouter.ai/docs/guides/overview/multimodal/image-understanding).

## Проверки

`npm test` в backend запускает сценарии без сети: выбор inspect без добавления, цепочка remove → add, автоматическое заполнение полей внутри add, оригинал и прозрачная версия, повторы между сообщениями, изменение описания/фото, устаревшие версии, неизвестные вложения, неоднозначность, отмена, сбой сохранения и сбой модели после записи. Отдельный тест поднимает настоящий HTTP API и проходит поток → браузерный обработчик → одноразовый результат → ответ агента. Проверяется удаление токенов при отключении клиента и делегирование выбранной темы общей службе трендов.

Живой smoke-тест использует настоящую модель для выбора инструментов и распознавания синтетической футболки, а затем общий репозиторий в изолированной fake-indexeddb:

```sh
cd backend
node --import tsx scripts/check-wardrobe-tools.mjs
```

Запрос идёт через `http://127.0.0.1:5175`; другой origin задаётся `WARDROBE_TEST_ORIGIN`. 18 октября 2026 получен PASS: модель сама вызвала `wardrobe_add_from_image`, вещь сохранена, 6715 байт оригинала совпали, после результата выполнен `wardrobe_finish`. Личный гардероб не изменялся. Реальный платный CV-вызов этим тестом не запускается; remove → add проверяется с подменённым обработчиком.

Браузерный сценарий обновлён под `tool_request` и проверяет отсутствие переключателя. Его выполнение и визуальная проверка остаются незавершёнными: Computer Use снова вернул `Sky Computer Use native pipe startup failed`. Проверки с fake-indexeddb не выдаются за браузерный прогон. Качество распознавания на разнообразных личных фотографиях ещё не измерено.

## Восстановление после отказа распознавания

Результат удаления фона остаётся в базе вложений и доступен следующему сообщению. Успешное распознавание также сохраняется рядом с фото (до трёх уточнений) и переносится в обработанную версию; повторное добавление может использовать эти поля без нового vision-запроса. Уже сохранённая вещь возвращается по её квитанции без вызова распознавания. Передача уже очищенного изображения в remove не запускает CV повторно.

API возвращает безопасные `code` и `retryable`. Браузер передаёт их модели вместе со ссылкой на сохранённое изображение; ошибка не превращается в общее исключение без контекста. Неразрешённый отказ vision даёт ответ `limited` с фактически выполненными действиями и предложением продолжить тем же фото через чат. Ручная форма и посторонние образы не подставляются вместо восстановления. Служебные `cutout-*`/`stylist-*` не отображаются в обычном ответе, включая прежние сообщения; исходные ссылки остаются в протоколе инструментов и истории.

Добавлены регрессии для цепочки «фон удалён → vision недоступна → следующее сообщение сохраняет ту же прозрачную версию», переиспользования полей после нового подключения, бесплатного резервного маршрута, отсутствия повторного CV и скрытия ID. Реальное повторное распознавание тестовой футболки и добавление через модель прошли; изначальный отказ пользователя на тестовом изображении в момент проверки не воспроизвёлся.
